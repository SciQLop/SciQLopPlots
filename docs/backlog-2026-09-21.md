# Backlog (2026-09-21)

## B1 — Let SciQLop tell product kinds apart (virtual products, vectors, spectrograms, ...)

**Not for SciQLopPlots to implement per kind.** SciQLopPlots should stay ignorant of what a
"virtual product" is. It should only offer the interface that lets SciQLop identify and
find such nodes itself.

What exists today (`include/SciQLopPlots/Products/ProductsNode.hpp`, `enums.hpp`):
- `ParameterType`: `NotAParameter, Scalar, Vector, Multicomponents, Spectrogram`. Fixed
  enum, describes the data shape only. No way to say "this is a virtual product".
- `metadata()`: free-form `QMap<QString, QVariant>`, set at construction. Feeds the search bar's
  suggestions (`ProductsView::refresh_completions()`), so any tag put there also shows up
  as a suggestion.
- `provider()`: one string, set at construction.

What is probably missing (to confirm with SciQLop before designing):
- A stable, non-search "kind" tag on a node, separate from `metadata` (which is presented
  to the user and searched) and from `ParameterType` (closed enum).
- A way to ask the model for nodes by kind or predicate without walking the tree from
  Python (`ProductsModel` has `node(path)` only).
- A signal or hook when a node of a kind is added or removed (needs `remove_node`, see
  the 2026-09-21 design), so a SciQLop-side panel can stay in sync.

Questions to settle first:
1. Does `metadata` + `provider` already do the job if SciQLop reserves a key (cheapest,
   no API change)? Then the gap is only a query helper.
2. If a dedicated tag is needed: open string vs registered kinds.
3. Should the tag be mutable after publishing, and does that need a `dataChanged`?

Related: `ProductsModel::remove_node` (design agreed 2026-09-21).
